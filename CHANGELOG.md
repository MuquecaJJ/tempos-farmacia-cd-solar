# Changelog

Todas as mudanças relevantes do projeto Cronômetro Operacional (Farmácia / CD Solar) ficam registradas aqui, em ordem cronológica reversa. Referências de bloco (B0, B1...) seguem a Seção 12 do `PLANO_CRONOANALISE.md`.

## 2026-08-17

### Adicionado

- **B7 — Export CSV**: `GET /api/painel/export`, Route Handler (não Server Action — é leitura pública de arquivo via link, não mutação disparada de formulário) protegido pelo mesmo cookie do painel (verificado explicitamente dentro do handler, já que o `proxy.ts` só cobre `/painel/:path*` e não `/api/painel/*`). Gera um CSV achatado com todas as 27 colunas da Seção 8.4 do plano (incluindo `fluxo`, resolvida via `corridas.fluxo_id` para medições de corrida, em branco para AVULSA/CICLO), separador `;`, BOM UTF-8 (`String.fromCharCode(0xfeff)`, evita ambiguidade de caractere literal no source) e escaping RFC-4180 (campos com `;`, `"` ou quebra de linha entre aspas, aspas internas duplicadas). Inclui todos os status (`VALIDA`, `DESCARTADA`, `SUSPEITA` — R05), sem filtro algum: a decisão de o que usar na análise é do analista, não da ferramenta. Link "exportar CSV" adicionado ao cabeçalho do painel.

### Verificado

- `npm run build` sem erros.
- Testado via curl com cookie de sessão: 401 sem cookie e com cookie inválido; 200 com o PIN correto. Conteúdo do CSV inspecionado byte a byte — BOM `EF BB BF` confirmado no início do arquivo, `Content-Disposition` com nome de arquivo datado. Testados os 3 status (`VALIDA`/`DESCARTADA`/`SUSPEITA`) e os 2 casos de origem (medição avulsa sem corrida vs. medição de uma corrida FLUXO, confirmando a coluna `fluxo` populada só no segundo caso). - **B6 — Dashboard**: painel em `/painel`, atrás de PIN (S3). Autenticação via `proxy.ts` (renomeação de `middleware.ts` no Next 16) protegendo `/painel/:path*` exceto a própria tela de login; a validação do PIN e a gravação do cookie (`httpOnly`, `secure`, `sameSite=strict`, 8h) acontecem em Server Actions (`app/painel/actions.ts`), não em Route Handler — é o padrão recomendado atual do App Router para mutações disparadas de formulário, e permite a tela de login inteira ser Server Component (sem JS necessário para autenticar). Todas as leituras do painel usam `lib/supabase-admin.ts` (novo cliente com service role, `import "server-only"`) diretamente nos Server Components — sem Route Handler intermediário, já que Server Components já rodam no servidor e nunca expõem a chave ao cliente (S6).
  - **Cobertura** (`/painel/cobertura`): tabela agrupada por processo, uma linha por atividade, com `n`/meta/% (semáforo vermelho/âmbar/verde) e última coleta. Filtros por processo, papel, natureza e tipo de coleta, calculados no cliente sobre os dados já carregados (sem refetch a cada filtro).
  - **Estatísticas** (`/painel/atividades`): por atividade — n, média, mediana, desvio-padrão, CV (sinalizado quando >0,30), mín, máx, p90, tempo por unidade e histograma; quebra AUTO×OBSERVADO lado a lado; quebra por turno e colaborador em `<details>` colapsado. Views agregadas por Processo, por Tipo de Atividade e tempo médio por etapa dentro de cada fluxo. Funções estatísticas puras extraídas para `lib/estatisticas.ts` (média, mediana, desvio-padrão amostral, percentil por interpolação linear, CV).
  - **Registros** (`/painel/registros`): lista paginada (50/página) com filtros por status e atividade, botão "marcar suspeita" por linha usando Server Action vinculada (`marcarSuspeita.bind(null, id)`) com `revalidatePath` — ação server-side conforme exigido pelo plano, sem alterar `status` de nenhum outro jeito (nunca deleta).
  - Ambas as páginas de leitura (`cobertura`, `atividades`) precisaram de `export const dynamic = "force-dynamic"` — sem isso o Next as pré-renderizava como HTML estático no build (sem nenhuma API dinâmica sendo chamada), o que serviria dados congelados do momento do build para um dashboard que precisa refletir a coleta em andamento. `registros` já é dinâmica por depender de `searchParams`.

### Verificado

- Testado via automação de navegador contra o banco real: login com PIN errado (mensagem de erro, sem cookie), login correto (redirect para cobertura), proxy bloqueando acesso direto a `/painel/cobertura` sem cookie (307 → `/painel`) e voltando a bloquear após logout. Cookie confirmado `httpOnly` (não aparece em `document.cookie`).
- Estatísticas conferidas manualmente contra os dados de teste inseridos (7 medições, 2 sessões AUTO/OBSERVADO): média, mediana, desvio-padrão, CV e p90 batendo exatamente com o cálculo manual, incluindo a quebra por turno e por colaborador.
- Marcar suspeita testado de ponta a ponta: status muda no banco, a linha some da lista de "marcar suspeita" disponível, e as estatísticas deixam de contar aquele registro (filtro `status = 'VALIDA'`).
- **Nota de ferramental**: a extensão Claude in Chrome apresentou clique não-registrando de forma intermitente nesta sessão (cliques via coordenada/ref não geravam eventos no app, confirmado comparando os logs do servidor). Contornado disparando os mesmos formulários via `form.requestSubmit()` no console — isso testa a submissão real do Server Action, não simula o resultado. Não há indício de que seja um problema do app; registrando para o caso de se repetir.
- Dados de teste (sessões e medições) removidos do banco após a verificação.

- **B5 — Modo CICLO**: rota `/c/[token]/ciclo/[id]` para repetição da mesma atividade. `CicloAtividade.tsx` com máquina de estados IDLE → RODANDO → CONFIRMACAO. Botão grande CICLO (âmbar) grava a duração desde o toque anterior e reinicia a contagem do ciclo sem parar o cronômetro total da corrida (mesma técnica de "lap" contínuo do B4); mostra cronômetro do ciclo atual, contador, média corrente e os últimos 3 ciclos com descarte individual (que apenas remove do estado em memória — a corrida ainda não existe no banco nesse ponto). Botão ENCERRAR (vinho, secundário) abre a confirmação. Diferente do B3/B4, a quantidade da corrida **não é digitada manualmente** — é derivada do número de ciclos efetivamente registrados (`ciclos.length`), evitando uma fonte de erro de digitação para um dado que a própria ferramenta já mede com precisão. SALVAR/DESCARTAR gravam 1 `corrida` (`modo='CICLO'`, `atividade_id` preenchido, `fluxo_id` null) + N `medicoes` com `ordem` renumerado sequencialmente a partir dos ciclos sobreviventes (independente de descartes intermediários). "Cancelar" durante RODANDO não grava nada, mesmo padrão do B3/B4.

### Verificado

- `npm run build` sem erros, incluindo a nova rota `/c/[token]/ciclo/[id]`.
- Fluxo completo testado com automação de navegador (Claude in Chrome, após reconexão) contra o dev server e o banco real: sessão de 4 ciclos com descarte individual de 1 deles (média recalculada corretamente, cronômetro do ciclo em andamento não afetado pelo descarte), encerrar, salvar com observação — `corrida.quantidade` refletindo exatamente os ciclos sobreviventes e `medicoes.ordem` renumerado sequencialmente (1, 2) sem gaps mesmo com o descarte no meio. Também testados cancelar em RODANDO (nenhum registro gravado) e descartar corrida inteira (status `DESCARTADA` propagado para as 2 medições filhas).
- Dados de teste (sessões, corridas e medições) removidos do banco após a verificação.

- **B4 — Modo FLUXO**: rota `/c/[token]/fluxo/[id]` para a corrida encadeada de etapas. `page.tsx` busca o fluxo, suas `fluxo_etapas` (ordenadas) e as atividades referenciadas. `CorridaFluxo.tsx` agrupa as etapas por `ordem` (etapas que compartilham `ordem` viram um grupo de variantes) e implementa a máquina de estados IDLE → SELECAO → RODANDO → CONFIRMACAO: cronômetro da etapa e cronômetro total da corrida, ambos derivados de `performance.now()`, sem intervalo morto entre etapas (o fim de uma etapa é o início exato da próxima, R01). Em grupos de variante, uma tela de seleção por checkbox antecede o cronômetro (múltipla seleção permitida — necessário no F1, onde uma NF pode trazer mais de um tipo de item, R10); cada variante selecionada vira uma medição separada, cronometrada em sequência. "Pular etapa" avança sem gravar medição (R09); no grupo de variante, pular descarta o grupo inteiro. Ao concluir a última etapa, o botão principal muda para "ENCERRAR CORRIDA", abrindo a confirmação: quantidade da corrida (sempre obrigatória, unidade = `fluxo.unidade_corrida`) e observação opcional, SALVAR grava 1 registro em `corridas` + N em `medicoes` (com `ordem` sequencial), DESCARTAR CORRIDA INTEIRA grava ambos com `status = 'DESCARTADA'` (propagação R03, feita na própria gravação já que corrida e medições nascem juntas no mesmo insert). Também é possível "cancelar" durante RODANDO/SELECAO (mesma decisão de UX do B3): nada é gravado, pois a corrida só é criada no banco na confirmação final.
- Extraídos para `lib/cronometro.ts` os helpers `formatarTempo`, `vibrar`, `adquirirWakeLock` e `liberarWakeLock`, antes duplicados apenas em `CronometroAvulsa.tsx` — o B4 precisou dos mesmos, e esse era o ponto (antecipado no plano) para deixar de duplicar.

- **B3 — Modo AVULSA**: rota `/c/[token]/avulsa/[id]` para o cronômetro de atividade isolada. `page.tsx` (Server Component) busca a atividade pelo `id`, faz `notFound()` se inexistente/inativa/fora do modo `AVULSA`. `CronometroAvulsa.tsx` (Client Component) com máquina de estados IDLE → RODANDO → CONFIRMACAO: cronômetro em fonte mono (`MM:SS.d`) calculado sempre a partir de `performance.now()` (R01), Wake Lock API com reaquisição em `visibilitychange`, `beforeunload` ativo durante RODANDO, vibração (`navigator.vibrate`) nos toques que gravam algo. Adicionado também um link discreto "cancelar" durante RODANDO (fora da especificação original, decisão tomada em conjunto com o usuário): aborta sem gravar nenhum registro, já que a corrida nunca chegou a PARAR.

### Verificado (B3)

Como as policies de RLS não estão commitadas nas migrations, este é um item pendente para o **B8 — Segurança**, não uma regressão do B3.

### Infraestrutura (Vercel)

- Diagnosticado e corrigido deploy de produção retornando 404 em todas as rotas: (1) Vercel Authentication (SSO) estava ativado no projeto, o que bloquearia o acesso dos celulares do CD (sem login na equipe Vercel) — desativado, pois a segurança do app já vem do `COLETA_TOKEN` (S1) e do PIN do painel (S3); (2) a deployment mais recente tinha o pacote de saída vazio (`lambda output: []`) — os logs de build mostravam as rotas geradas normalmente, mas o empacotamento final não as anexou, provavelmente por causa da transição do preset de build de "Other" para "Next.js" feita no meio do processo. Um novo deploy (`vercel --prod`) resolveu, com os passos específicos do Next.js (`Applying modifyConfig from Vercel`, `Detected Next.js version`) aparecendo corretamente nos logs desta vez.
- Configuradas no projeto Vercel (Production e Preview) as env vars `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` e `PAINEL_PIN`, que estavam ausentes (só `COLETA_TOKEN` existia).

### Alterado

- **Catálogo passa a ser filtrado por macroprocesso, não por papel.** Mudança de escopo pedida após teste do B2: a tela de sessão ganhou um campo de seleção de **macroprocesso** (um dos 6 `processos` já existentes), exibido logo após o colaborador. O papel continua sendo perguntado (para as quebras estatísticas do dashboard no B6), mas deixou de determinar o que aparece no catálogo. Migration `0002_sessao_processo.sql` adiciona a coluna `processo_id` (not null) em `sessoes`. `CatalogoAtividades` foi simplificado: filtra atividades e fluxos diretamente pelo `processo_id` de cada um, sem precisar inferir o papel via join em `fluxo_etapas`.
